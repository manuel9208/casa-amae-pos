3. MULTI-TENANT DESDE EL DÍA 1
=====================================================
Modelo: empresas (id, slug único, nombre, activo, zona_horaria, moneda, dominios_permitidos)
        sucursales (id, empresa_id, nombre, direccion, lat/lon, zona_horaria opcional, activo)
        todas las demás tablas llevan empresa_id NOT NULL con FK, e incluyen sucursal_id cuando aplica.
- Unicidad SIEMPRE compuesta con empresa_id: UNIQUE(telefono, empresa_id), UNIQUE(usuario, empresa_id), etc. Nunca únicos globales.
- Considera llaves foráneas compuestas (id, empresa_id) en las relaciones críticas para que la BD impida cruzar empresas.
- Defensa en profundidad (propónmelo en el diseño): Row Level Security de PostgreSQL con SET LOCAL app.empresa_id dentro de cada transacción.
- Identificación de la empresa: el frontend manda el header X-Empresa-Slug (variable de entorno por despliegue).
  El slug es PÚBLICO y por sí solo NO da acceso a nada.
  Si hay token, empresa y sucursal salen del token; si el header no coincide con el token, responde 403.
  Sin token, solo se permiten las rutas explícitamente públicas.
- La capa repositories rechaza (lanza error) cualquier consulta sin empresaId. Entrega un script `npm run verificar:tenant` que revise con grep que ninguna query de repositories carezca de empresa_id.
- Sucursales: el alcance de cada usuario se guarda en el token (sucursales permitidas). Todo endpoint operativo filtra por empresa y por sucursal permitida.
- Zona horaria y moneda por empresa/sucursal (nada de zonas horarias hardcodeadas). Se guarda en UTC y se muestra en la zona de la sucursal.
- Alta de una empresa nueva: comando y pantalla de adminglobal que crean, en una sola transacción, empresa + sucursal principal + usuario admin + configuración por defecto, y generan la carpeta public/clientes/<slug> con una plantilla.

4. SEGURIDAD (DENEGAR POR DEFECTO)
=====================================================
- routes/index.js aplica resolverTenant y autenticar a TODO. Las rutas públicas se declaran en una lista blanca explícita (login, identificación de cliente final, catálogo público, webhooks firmados). Una ruta nueva nace protegida.
- Guards componibles: autenticar -> requerirRol(['admin','gerente']) -> requerirPermiso('modulo') -> requerirSucursal. Los permisos son por usuario (JSONB). Quien otorga un permiso debe tenerlo él mismo (anti-escalamiento) y el backend valida de forma genérica sin conocer los nombres de los módulos.
- Jerarquía de roles con nivel_jerarquico: solo se opera sobre usuarios de nivel estrictamente mayor. El rol adminglobal es invisible e inmodificable por la API.
- Tokens firmados con HMAC (sin dependencias, o JWT), con SESSION_SECRET de 32 caracteres o más. Claves derivadas por dominio (empleado, cliente, canje) para que un token de un tipo nunca valide como otro. Payload: { uid, eid, sid[], rol, exp }.
- Contraseñas, PIN y NIP con hash (argon2 o bcrypt) desde el inicio. NUNCA se devuelven en respuestas ni se mandan por correo (para recuperar: código de un solo uso con expiración).
- Límite de intentos (login, PIN, códigos) persistido en BD o Redis, no en memoria. Bloqueo temporal por usuario e IP. Cabeceras con helmet. CORS con lista de dominios permitidos por empresa (no '*').
- Validación de entrada en cada endpoint (validators) y serializers de salida. Consultas siempre parametrizadas; los nombres de columna salen de listas blancas.
- Los precios y totales se recalculan SIEMPRE en el servidor con /calculos. El cliente nunca fija montos ni estados privilegiados.
- Subidas de archivos: validar tipo y tamaño, carpeta empresa_<id>/..., credenciales de Cloudinary resueltas por empresa y borrado del archivo anterior al reemplazar.
- Bitácora de auditoría (tabla bitacora: empresa, sucursal, usuario, acción, entidad, antes/después) para acciones críticas.
- Sockets: autenticación con token en el handshake (no solo el slug); salas empresa_<id> y empresa_<id>_sucursal_<id>; PROHIBIDO io.emit global; catálogo de eventos en sockets/eventos.js. Los eventos de alerta se filtran siempre por empresa y sucursal.
- Manejo de errores centralizado: respuestas limpias para el usuario, el detalle técnico solo en logs (con request id), sin secretos en logs. Endpoint /salud para monitoreo.

5. CONFIGURACIÓN Y VARIABLES (.env MÍNIMO)
=====================================================
Solo van en el .env global: DATABASE_URL, SESSION_SECRET, MASTER_KEY (cifrado), PORT, CORS base, SUPERADMIN (arranque inicial). Todo lo demás va en una pantalla de adminglobal:
- Tablas variables_empresa y variables_sucursal (clave, valor cifrado con AES-256-GCM usando MASTER_KEY, descripción).
- Catálogo de claves disponibles que solo adminglobal puede ampliar.
- resolverVariable(empresaId, sucursalId, clave): primero la sucursal, luego la empresa y por último el .env global.
- Las pantallas muestran los valores enmascarados. "Revelar" requiere adminglobal y queda en la bitácora. Nunca se envían secretos al frontend normal.
- Candados comerciales por empresa (tabla empresa_modulos: módulos y funciones activas por plan), con doble validación: visual en el frontend y real en el backend.

6. BASE DE DATOS Y MIGRACIONES
=====================================================
- database/schema.sql es el ÚNICO archivo para CREATE y ALTER. Solo crece y todo es idempotente (IF NOT EXISTS, ADD COLUMN IF NOT EXISTS, ON CONFLICT DO NOTHING). Va dividido en bloques numerados.
- runSchema.js ejecuta cada sentencia por SEPARADO, nunca como un bloque único. Así, si una sentencia falla, no se revierte todo en silencio. Registra cada error con claridad y continúa o detiene según la gravedad. Render lo ejecuta en cada deploy con: npm install && npm run db:sync.
- Cada tabla nueva nace con empresa_id (y sucursal_id si aplica), índices por empresa_id y uniques compuestos.
- Dinero con NUMERIC (o enteros en centavos), nunca float. Borrado lógico (activo=false) donde haya histórico.
- Respaldo antes de cambios destructivos. Prohibidos los DROP automáticos.

7. WHITE-LABEL: IDENTIDAD VISUAL Y ESTÁTICOS POR CLIENTE
=====================================================
- Estático por cliente (lo que el navegador lee antes de que arranque React): front/public/clientes/<slug>/ con favicon, logo192, logo512, manifest.json y el título de la página.
- Un solo script genérico: `npm run dev:cliente -- <slug>` y `npm run build:cliente -- <slug>`. El script scripts/set-cliente.js valida que exista la carpeta, copia sus archivos a la raíz de public y escribe .env.local con VITE_EMPRESA_SLUG=<slug> y VITE_API_URL. Así no hace falta un script en package.json por cada cliente.
- Dinámico (en tiempo real desde BD y filtrado por empresa): nombre, logo, colores, fuentes, horarios y moneda. Se inyectan como variables CSS (--c-primario, --c-secundario, etc.). El nombre real del negocio NUNCA queda hardcodeado en código ni en archivos compartidos.
- Cada despliegue de Vercel (un proyecto por cliente) apunta al mismo repositorio y al mismo backend.
