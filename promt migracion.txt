[ARQUITECTURA Y ESTRUCTURA DEL PROYECTO]
Marca Blanca (White-Label): El sistema es 100% personalizable por negocio. Los estilos (colores primarios, fondos, fuentes, logos) se inyectan dinámicamente desde la tabla configuracion mediante variables CSS en App.js, filtrados siempre por empresa_id.

Estructura Frontend (src/components/), modularizada por roles:

/admin: Panel de administración, inventarios, catálogos, reportes y configuración.
/caja: Punto de venta principal, control de mesas, cobros y confirmación de pedidos.
/cocina: KDS (Kitchen Display System), control de mermas, tiempos y comunicación de faltantes.
/kiosco: Interfaz de cliente, menús interactivos, fidelidad (NIP) y carrito.
/empleado: Portal personal del trabajador (Nómina, asistencia, limpieza).
Archivos raíz: App.js, Caja.js, Cocina.js, Kiosco.js, PantallaTV.js.
Backend (api.js): Arquitectura RESTful modularizada con controladores por entidad (configCtrl, pedidoCtrl, mermaCtrl, proveedorController, insumoController, usuarioController, huellasController, cocinaOperativaController, comboController, mensajeController, corteController, notificacionController, etc.) e integración profunda con WebSockets (socket.io) para actualizaciones en vivo.

Resolución de Tenant: Cada request HTTP se resuelve a una empresa mediante resolveTenant.js (middleware que lee el header X-Empresa-Slug enviado por apiFetch.js desde el frontend, consulta la tabla empresas por slug, e inyecta req.empresa_id en cada controlador). El frontend de cada negocio define su propio slug vía variable de entorno REACT_APP_EMPRESA_SLUG en Vercel (tipo "Config", NUNCA "Secret", porque REACT_APP_* siempre queda expuesto en el bundle del navegador).

Migración de esquema: El archivo config/migracionMultiTenant.js contiene dos bloques críticos que corren al arrancar el backend (iniciarServidor en index.js):

Bloque A (crearTablasBaseSiNoExisten): crea tablas nuevas con CREATE TABLE IF NOT EXISTS ya con columna empresa_id INTEGER REFERENCES empresas(id) incluida desde el diseño.
Bloque B (agregarEmpresaIdATablas): un único db.query() con decenas de ALTER TABLE ... ADD COLUMN IF NOT EXISTS empresa_id para tablas preexistentes de la era mono-tenant. ⚠️ Esto corre como "simple query" (múltiples sentencias en un string), lo que significa que Postgres las envuelve en una transacción implícita: SI UNA SOLA SENTENCIA FALLA (ej. una tabla que no existe, como pasó con reporte_mermas), TODO EL BLOQUE SE REVIERTE EN SILENCIO, dejando decenas de tablas sin empresa_id sin ningún error visible aparte del primero.
Base de Datos (PostgreSQL): Esquema normalizado con control transaccional estricto (pedidos, histórico de cortes, cortes logísticos, mermas, puntos de fidelidad y rendimiento de insumos), con aislamiento por empresa_id en prácticamente todas las tablas operativas.

[REGLAS OPERATIVAS DEL NEGOCIO - BUSINESS LOGIC]
Flujo de Pedidos (Kiosco -> Caja -> Cocina): Todo pedido nuevo nace con estado 'Pendiente'. La Caja debe interceptarlo en "Por Confirmar". La Cocina (KDS) es ciega a la orden hasta que el cajero la autoriza y pasa a 'Preparando'.
Finanzas y Auditoría Blindada: Separación estricta de métricas. El "Corte de Repartidores/Logística" se audita independiente del "Corte de Caja" general. Los gastos se consultan y calculan en vivo leyendo la BD para evitar discrepancias. Los montos de proveedores se procesan por lotes vía actualizarEstadoGastoBulk, afectando stock_actual de insumos o stock_preparado de productos según corresponda, siempre filtrado por empresa_id.
Tiempo Real: Toda acción crítica (nuevo pedido, actualización de inventario, cambio en catálogo, llamado de mesero, alerta de stock a proveedores) debe emitir un evento por WebSockets. Los eventos de alerta a administradores (alertarAdministradores) deben filtrar suscripciones push y sockets SIEMPRE por empresa_id, nunca de forma global al sistema completo.
Aislamiento Multi-Tenant Absoluto: NINGUNA query de lectura, escritura o alerta puede cruzar datos entre empresas. Todo WHERE, JOIN, UPDATE y DELETE debe incluir empresa_id = $X explícito. El patrón de bug ya detectado y corregido en el pasado: tomar "LIMIT 1" de una configuración SMTP/negocio sin filtrar por empresa (ver "Patrón 23" ya corregido en proveedorController.js, que ahora resuelve nombre/SMTP por la empresa dueña de cada proveedor con caché, para no repetir consultas si varios proveedores pertenecen a la misma empresa).

METODOLOGÍA DE MIGRACIÓN VALIDADA (referencia a conservar para un posible 5º negocio a futuro):

En la BD ORIGEN del negocio: asegurar que tenga TODAS las columnas empresa_id (correr manualmente el bloque completo de ALTER TABLE si el backend nunca llegó a crearlas por el bug de reporte_mermas).
Insertar fila "puente" en la tabla empresas de origen (mismo id que tendrá en destino) para que el backfill de empresa_id no falle por FK.
Backfill automático: DO $$ ... FOR r IN SELECT table_name FROM information_schema.columns WHERE column_name='empresa_id' ... EXECUTE format('UPDATE %I SET empresa_id = X WHERE empresa_id IS NULL', r.table_name) ... $$ — detecta TODAS las tablas solas, sin lista manual.
⚠️ CUIDADO: tablas "singleton por empresa" (configuracion, configuracion_financiera, configuracion_proveedores, configuracion_operativa, configuracion_biometria, configuracion_asistencia, dist_configuracion, ia_configuracion) pueden tener MÁS DE UNA fila huérfana (residuos de otras empresas con bugs previos) — en ese caso el UPDATE masivo con WHERE empresa_id IS NULL falla por índice único (ej. idx_config_financiera_clave_empresa, idx_config_proveedores_empresa_unica). Solución: actualizar por id explícito, no a ciegas.
Quitar TODAS las FK temporalmente (respaldar en tabla TEMP con pg_get_constraintdef, hacer DROP CONSTRAINT en bucle).
Offset de IDs:
a) PRIMERO mover el id propio de las tablas "padre" (usuarios, clientes, mesas, productos, insumos, clasificaciones, proveedores, catalogo_ingredientes, estaciones_cocina, recetas, compras_insumos, pedidos, credenciales_biometricas, registro_asistencias, gastos_proveedores, empleados_dispositivos, promociones, suscripciones_push, cupones, combos, estacion_clasificacion, configuracion*, dist_configuracion, ia_configuracion, historico_cortes, log_produccion_items, surtidos_borrador).
b) DESPUÉS las columnas que REFERENCIAN esas tablas — usando mapeo automático vía information_schema.table_constraints + key_column_usage + constraint_column_usage ANTES de haber quitado las FK (⚠️ BUG CONOCIDO Y YA RESUELTO: si se consulta el mapa DESPUÉS de quitar las FK, el mapa sale vacío y columnas como pedidos.chef_id, catalogo_ingredientes.clasificacion_id quedan sin offset. Fix: reconstruir el mapa desde el propio backup de FK guardado, parseando FOREIGN KEY (col) REFERENCES tabla(id) con regex, y usar operación módulo (col % 1000000) + nuevo_offset para neutralizar cualquier doble-offset o offset parcial residual).

[REGLAS ESTRICTAS DE DESARROLLO Y REFACTORIZACIÓN - LEYES INQUEBRANTABLES]
Preservación Estricta: NO cambies lógicas, código, ni funciones que el usuario no haya reportado o solicitado modificar explícitamente.
Precisión Quirúrgica en Código de Aplicación: Sé exacta en los cambios de componentes React/controladores. No introduzcas efectos secundarios que rompan el estado global, los WebSockets o la inyección de estilos de la Marca Blanca.
ENTREGA DE CAMBIOS: Para CUALQUIER corrección de código (JS/React) o script SQL puntual, entrega SIEMPRE en formato ANTES/DESPUÉS mostrando ÚNICAMENTE el fragmento específico a cambiar (no el archivo completo), salvo que el usuario pida explícitamente el archivo entero. Esto aplica tanto a:
Ajustes de controladores backend (ej. una query que falta filtrar por empresa_id).
Componentes React.
Scripts SQL de corrección puntual (ej. "este INSERT necesita el offset en tal columna").
Formato esperado:
❌ ANTES: [fragmento exacto tal cual está]
✅ DESPUÉS: [fragmento corregido]
Cuando se trate de archivos NUEVOS completos (ej. una migración SQL nueva de cero, o un componente nuevo desde cero), sí se entrega completo.
UI/UX Premium e Inmersiva: Siempre busca excelencia visual y responsiva (Tailwind). Mobile-first, Desktop-optimized.
Alertas Custom (Cero Nativos): PROHIBIDO alert(), confirm(), prompt(). Todas las notificaciones vía modales UI personalizados.
Comunicación Proactiva al Cliente: Notificaciones automáticas (Push/UI/WhatsApp) sobre estado del pedido.
Sincronización Total (Sockets): Mantener y optimizar actualizaciones con Sockets en vivo, SIEMPRE filtradas por empresa_id cuando emitan a salas/clientes específicos de un negocio.
Principio DRY: No duplicar lógicas. Reutilizar componentes, hooks y utilidades existentes (ej. Gestor de Mermas compartido entre Caja y Cocina).
Convención de Nombres: PascalCase para componentes (ModalConfirmacion.js), camelCase para funciones/hooks (useCajaCentral.js).
Multi-Tenant por Defecto: CUALQUIER query SQL nueva que se proponga, sugiera o corrija DEBE incluir el filtro empresa_id explícito salvo que el usuario indique lo contrario o se trate de una tabla de catálogo global del sistema (ej. [SISTEMA] Catálogo de Variables en la tabla empresas, slug __catalogo_variables__, que NO es un negocio real).
Iniciativa de Mejora: Evalúa proactivamente mejoras operativas, visuales o de rendimiento sin romper lo existente — y prioriza detectar posibles fugas de aislamiento multi-tenant (cruces de datos entre empresas) como parte de esa iniciativa.
